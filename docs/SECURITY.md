# Security

See also: [ARCHITECTURE.md](ARCHITECTURE.md), [DECISIONS.md](DECISIONS.md), [DEVELOPMENT.md](DEVELOPMENT.md).

Nothing here is implemented yet except repo-level controls (§5). Application controls are **[Proposal]** or **[Design]** until built and tested. Evidence tags follow [ARCHITECTURE.md](ARCHITECTURE.md): **[Verified]** (checked against a cited official page), **[Unverified]**.

## 1. Principles
- Whatever the repository's visibility, no secrets, tokens, mailbox data or personal messages may enter Git, issues or pull requests.
- Email content is untrusted input; it is data, never instructions.
- Least privilege: read-only first; modification scopes only when needed and separately consented.
- No permanent deletion by the application.
- Skills/agents/LLMs do not grant permissions (§6).
- **Zero Additional Cost is mandatory and approved** (§1a).

## 1a. Zero Additional Cost policy (approved)
The project must incur zero additional financial cost. Security-relevant consequences: no Google Cloud Billing or billing account, no paid Cloud services, no paid LLM/AI APIs, no paid GitHub features (including the plan upgrade that would unlock native private-repo secret scanning), no paid hosting/monitoring/databases, no paid dependencies. A budget alert is **not** protection against charges; if a service has no hard spending cap and its billing status is unknown, it stays disabled. Claude Code is a development tool outside this objective; the application never depends on Claude API calls. Provider free tiers can change; nothing here promises any provider stays free. Cost verification is a mandatory acceptance criterion for every milestone ([ROADMAP.md](ROADMAP.md)).

## 1b. Gmail scope and capability facts
- `gmail.readonly` reads data and has no modification ability **[Verified]**.
- `gmail.modify` also allows composing and **sending** mail **[Verified]**. Our ban on sending, forwarding, replying and permanent deletion is therefore **an application policy, not an OAuth-enforced limit**. Permanent deletion is not exposed; `https://mail.google.com/` is never requested.
- A separate token file does not by itself create a reliable capability boundary. The required controls (read-only client types, execute-only write adapter with an operation allowlist, separate credentials, approval/plan validation) are specified in [ARCHITECTURE.md](ARCHITECTURE.md) §3 as a design requiring implementation validation.

## 1c. Write authorization and Gmail request boundary (M4C-B1, offline code only)
- **Live use was a single, owner-approved canary.** The code and tests use fake credentials, a fake Keychain and a fake HTTP connection. One real single-message archive canary was then executed once under the owner's explicit approval (redacted summary: `M4-CLOSEOUT.md`); live execution is disabled again by a source constant, the write grant was revoked and the local write token removed. Nothing is authorized to run live now.
- **Isolation:** the write scope is defined in exactly one module (`oauth_write.py`); the write token lives in its own Keychain item (service `gmail-intelligence-write`, item `oauth-token:gmail.modify`) with its own client file (`client_secret_write.json`). There is no fallback to or from the read-only token, and ordinary commands never touch the write item (tests enforce this). A separate Google Cloud project is the intended setup, but it is **not by itself** a security guarantee.
- **Revocation is project-wide at Google** (its documentation says it removes all scopes previously granted to the project), so a write client in the SAME project as the read-only client could take the read-only authorization down with it. Before any operation that could create or revoke a write grant (`login-write`, `revoke-write`, the cleanup of a rejected login), the tool verifies offline and fail-closed: both client ids have the recognized `NUMBER-RANDOM.apps.googleusercontent.com` form, they are not equal and do not share a project number, the read-only client file is present and valid, and the owner's attestation (recorded by `auth setup-write --confirm-separate-project`, stored as fingerprints only and bound to BOTH client files) still matches. A different project number is necessary evidence of a separate project, not proof, and the attestation is the owner's word: the tool cannot see Google's side. Client ids and secrets never appear in messages.
- **Scope is not the boundary.** `gmail.modify` also allows reading content, trashing, drafts and sending. The restriction to archiving is **an application policy** enforced by `gmail_write_policy.py` at the transport: only `GET profile`, `GET messages/{id}` (minimal/metadata), `GET threads/{id}` (minimal) and `POST messages/{id}/modify` whose body is exactly "remove INBOX" are ever sent. Everything else (send, drafts, threads.modify, trash, untrash, batchModify, batchDelete, insert, labels, settings, history, batch/upload endpoints, other hosts, redirects, method overrides, token-bearing query parameters, ambiguous encodings) is denied before any network dispatch. Anyone who obtains the token can still do more outside this tool.
- **No automatic retry or refresh in the transport.** A mutation is sent at most once per call; a timeout, 5xx, network error or malformed answer is reported as an UNCERTAIN outcome (to be recorded as `UNKNOWN`). Redirects and proxy environment variables are never followed or read. Token refresh and revocation use a separate OAuth request pinned to exactly one Google URL each, never the Gmail transport.
- **Reads are minimal by construction.** Every allowed GET must carry one of a few fixed `fields` projections (profile: email address only; message: labels, or labels plus the `From` header; thread: labels of its messages), so even a direct call to the transport cannot return snippets, subjects or bodies. Argument types are exact (`str`/`bytes`/`dict`); mutable buffers and subclasses are refused.
- **Mutation outcomes are conservative.** Refusals before dispatch (policy, budget, expired token) are definite. Once dispatch may have begun, every unclear result of the single modify request (timeout, interruption, redirect, oversized/malformed/unexpected answer, unexpected exception, even a failure while creating the connection) is an UNCERTAIN outcome to be recorded as `UNKNOWN` and reconciled; only a well-formed Gmail error document whose code matches the HTTP status counts as a definite rejection.
- **Responses must be completely framed.** A body shorter than its Content-Length, a truncated or unterminated chunked body, Content-Length together with Transfer-Encoding, repeated or malformed Content-Length, a transfer or content coding other than chunked/identity, and non-bytes bodies are never accepted: UNCERTAIN for the mutation, a read error for reads. Nothing is retried.
- **Verified account gate.** Nothing can be modified until `verify_account()` has succeeded against the live profile (a separately approved live step). The gate is a flag on the private transport that both the transport entry point and the wire-level dispatch check before a modify request, so the adapter's own private helpers cannot bypass it; a transport serves exactly one adapter (no cross-account reuse). A mismatch, a failed or malformed lookup, a missing expected account or any later authorization error locks it again. Code that deliberately writes the private flag can still bypass it: this is a boundary against mistakes, not against hostile code in the same process.
- **A rejected login does not leave a live grant behind (best effort).** If Google issued a grant but this tool refuses it (wrong scope, foreign client, no refresh token, profile failure, wrong account, Keychain failure), the new grant is revoked at Google and the outcome is reported as revoked / revocation failed / not attempted - never as "undone" unless Google answered HTTP 200. For the scope-change case the installed oauthlib raises a plain `Warning` that carries the parsed token response on the exception (the session stays empty); that payload is used only for that exact shape and only after strict validation, and is never printed. Revocation is not attempted when no handle exists, when separation from the read-only project cannot be verified, when a stored credential exists or the Keychain cannot be checked (the new grant might be the same one), or when the token equals the stored one; a stored credential is never replaced or revoked by a new login.
- **Only HTTP 200 confirms a revocation.** Google documents HTTP 200 for success and HTTP 400 "along with an error code" for errors, without listing the codes. Therefore no 400 is a confirmation - not even an `invalid_token` body, which is reported as "the token may already be invalid" while the local token is kept (remove it locally with `auth logout-write` if you accept that). Redirects, other statuses, unreadable bodies and transport failures are not confirmations either. This has NOT been verified against Google.
- **Refresh is explicit and validated.** The refresh result must report exactly the write scope and a complete token, or it is refused and the stored record stays unchanged. Status and read commands never refresh; the future M4C-C orchestration must call the refresh explicitly (the transport itself never does).
- **A failed command does not necessarily undo Google consent.** Automatic revocation after a rejected login is best-effort, never guaranteed. An unexpected software failure or a crash or interruption after the browser consent (for example between the consent and the Keychain write) can leave a Google grant active, and the CLI may not be able to say so. The handling is deliberately narrow: it only runs for the known rejection paths, and it is never broadened to arbitrary exceptions, because a broader cleanup could revoke a grant that belongs to an existing authorization. The owner therefore always has a manual path: inspect and revoke the write project's access in the Google Account (Security > Third-party access) after any failed or interrupted `auth login-write`.
- **Trusted observations and dispatch metadata (M4C-C1).** Evidence recorded as `TRUSTED_ADAPTER` must come from a one-time, account- and message-bound `TrustedObservation` issued by a verified archive adapter; an ordinary caller cannot type that source. This is an in-process guard, not a cryptographic one, and an observed state is never proof of authorship. Transport exceptions say whether anything could have been sent (`dispatched`, false only at explicit pre-transmission refusals); a complete HTTP error to a POST is not proof of non-effect, so such outcomes are `UNKNOWN` and reconciled, never retried. Ordinary evidence must be the exact `Evidence` type and is always stored as `CALLER_SUPPLIED`. The adapter's injected clock is trusted infrastructure (a controlled UTC clock in production); observations are not bound to an execution or plan id, so the C2 executor must prevent cross-execution reuse.
- **Single-item fake-only executor (M4C-C2).** Library only, not reachable from the CLI; it accepts only the final fake test mailbox type (no credentials, factory or transport can be supplied), owns its clock, requires every trusted observation to carry the execution-bound context the state machine derives, commits the intent before one POST, never retries, and treats anything possibly sent as `UNKNOWN`. These are in-process structural limits, not protection against malicious code in the same process.
- **Fake-only batch execution (M4C-C2b).** Library only; it repeats the single-item flow per item (one mutation path), stops at the first ambiguous or unsafe result, never retries or resumes an uncertain item, runs one slice per call and leaves continuation to the owner's confirmation. The same in-process limits apply.
- **Recovery and fake undo (M4D).** Library only. Recovery reconciles from fresh bound observations and never mutates; an undo needs its own typed owner authorization, one intent and one fake mutation, never rewrites the original APPLIED history, and is implemented only inside the fake mailbox (the real write boundary stays archive-only).
- **Disabled real-execution boundary.** `LiveMailbox` / `cleanup_live` reuse the fake-only per-item flow over the genuine archive-only adapter, are refused by (and refuse) the fake-only APIs, and are switched off by a `False` source constant that nothing changes; no CLI path, no live undo, no write-policy change. Offline-tested only; see the pre-canary checklist in CLEANUP.md.
- **Disabled single-message canary entry point.** `run_canary` refuses first while the source constant is `False`, needs a separate typed owner confirmation and a one-target execution, reuses the shared live executor, and has no CLI, environment or configuration path. Readiness and the approvals still required: `docs/CANARY.md`.
- **Canary exception and canary-only live execution (disabled).** A narrow, hashed one-message exception waives only the age and classification-type rules (never `SENT`, protections, unread, important, user labels, mixed threads or any executor check); live execution requires the private permit of `run_canary`, one target in one slice and the recorded owner confirmation; the owner entry point's local preparation (`describe`, `plan`) touches only the index, and its `run` refuses before the index or any credential store while the switch is `False`. See `docs/CANARY.md` section 5.
- **Local logout is not revocation.** `auth logout-write` deletes only the local token; `auth revoke-write` explicitly revokes the grant at Google first. `auth status-write` is local only and never refreshes.
- **Not independently verified:** real Google behaviour (headers, error bodies, the `modify` response), the system CA store used by the stdlib TLS context on the owner's Python, Keychain access prompts, and whether revoking one client's grant leaves another client's grant untouched. These need a separately approved live stage.

## 1d. M5 inbox organization boundary (local only)
- Every `labels` command (hygiene report, recommendations, proposed rules, filter suggestions, label-change plans, local approvals) reads and writes **only the local SQLite index**. None of them imports or calls the Gmail adapter, OAuth, the Keychain or any write module (static tests enforce this), and none requests a new OAuth scope. In particular no filter-management scope is requested: filter suggestions are text, never a filter.
- No label plan can be executed: there is no execute function, and an approval is a local ledger record that grants nothing. `LIVE_EXECUTION_ENABLED` stays `False`.
- Label names and sender addresses are private mailbox content: hidden by default, sanitized when shown, never written to the audit log or to GitHub.
- Label-plan audit events share the M4 hash chain (tamper-evident, not tamper-proof, as described in `cleanup_audit`). Schema v6 is additive and migrated after an automatic verified backup.
- Limits: a local database can be rewritten by anyone who controls the macOS account; label-plan freshness is judged against the last scan, not live Gmail; Gmail's behaviour for label create/rename/nest/merge is unverified. See [LABELS.md](LABELS.md).

## 1e. Dashboard server boundary (M6, local only)
- `dashboard serve` runs a standard-library HTTP server on `127.0.0.1` only (no host option). It serves `GET`/`HEAD` only, requires a per-launch bearer token on every `/api/` request (delivered as a URL fragment, held in memory, compared in constant time, never stored or logged), validates `Host` exactly (DNS rebinding), checks `Origin` and `Sec-Fetch-Site`, sends no CORS headers and a strict CSP, and opens the index with SQLite `mode=ro` (never migrating). It imports no Gmail, OAuth, Keychain or write module and has no mutation endpoint; static tests enforce this.
- The UI renders mailbox-derived text only as text (no `innerHTML`, no `eval`), loads nothing from the network, sets no cookie and stores only language and appearance locally. Sender addresses and label names are hidden by default.
- Limits: local malware running as the same macOS user can read the index file and the server's memory; the token does not defend against that. See [DASHBOARD.md](DASHBOARD.md) section 4.

## 1f. M7 sync boundary (design only; not implemented)
- Incremental sync uses the existing `gmail.readonly` scope and one new read-only adapter method (`history.list`, ids only); no new scope, no write method, no new dependency; the write boundary of §1c is untouched and `LIVE_EXECUTION_ENABLED` stays `False`.
- **Single writer.** One `running` run per account (database-enforced) with a fenced 5-minute lease: an active lease is never taken over, a stalled former owner cannot commit, and the process id is never trusted. Sync does not run during an M4 execution and an execution cannot be reserved during a sync.
- **Plan safety (fail-closed).** While the index freshness is uncertain (no checkpoint, sync running or interrupted, `NEEDS_RECONCILE`, an active, interrupted or failed full scan, or a checkpoint older than 24 hours) plan creation, review, approval and execution reservation are refused with `SYNC_NOT_HEALTHY`; the refusal writes nothing and is not counted as a failed confirmation. Sync never edits a plan, an approval or the audit log; a changed message makes plans that contain it stale through their item digests.
- Tombstones hold message ids only; reports and logs stay aggregate (no addresses, label names, ids or paths). The maintenance report is manual and read-only and never repairs or contacts Gmail.
- Limits: the local database can be rewritten by anyone who controls the macOS account; Gmail does not document history ordering, duplicates or truncation, so the design never relies on them and a silently truncated history response remains a documented residual risk; the Gmail quota page lists a billing threshold that must be re-confirmed before live use. See [SYNC.md](SYNC.md).

## 3. Reversibility classification
| Operation | Reversible? | Notes |
|---|---|---|
| Local analysis, classification, planning | Yes | No external effect |
| Add/remove label | Yes | Undo data recorded |
| Archive (remove INBOX) | Yes | Re-add INBOX |
| Move to Trash | Yes, until Gmail empties Trash after 30 days **[Verified]** | After auto-purge: **irreversible** |
| Create Filter | Yes (delete filter) | Effects on already-routed future mail are not retroactively undone |
| Permanent delete / empty Trash | **No** | **Forbidden** in app |
| Sending/forwarding mail | **No** | **Forbidden by application policy** (not OAuth-enforced under `gmail.modify`) |
| Disclosure to external AI provider | **No** (cannot be recalled) | Off by default, opt-in |
| Token leaked | Revocable, but exposure window is irreversible | Rotate/revoke |

### 5.3 Local scanner: behavior and limits
- Scans the **exact staged blobs** from the Git index (not the working tree), enumerating with NUL-delimited Git output and rename/copy detection disabled, so every added/modified/type-changed entry is scanned under its destination path regardless of Git's rename/copy classification. Deleted entries are skipped.
- Fails closed: Git failures, unreadable blobs, size mismatches, unmerged index entries and unexpected exceptions exit with status 2 and block the commit. Findings exit 1.
- Output contains only an escaped path, line number and rule name; never matched content.
- Symlinks are not followed (their target text is scanned); submodule and other unusual entry types are blocked; blobs over 5 MiB are blocked (deterministic, not skipped); binary blobs are scanned as bytes and never printed.
- Sensitive filenames are matched case-insensitively (`.env*`, token/credential/client-secret JSON, keys/certificates, mail exports, SQLite files). The placeholder exemption applies only when the *entire* assigned value is an obvious placeholder.
- **Remaining bypass risks:** `git commit --no-verify`; clones where the hook is not enabled; secrets not matching the regex rules (custom formats, split/obfuscated, base64, compressed/archived content, non-UTF-16 exotic encodings); entropy-based detection is absent; low-entropy passwords; the hook runs only locally and not in CI. It reduces risk and is not a guarantee. Gitleaks may be evaluated later (dependency review required; Q10).
- Tests: `python3 -I -m unittest discover -s tests` (stdlib only, temporary repos, synthetic data).

## 6. Skills and agents policy
A Claude Skill is instructions and helper tooling. It **does not grant Gmail API permissions**; permissions derive only from OAuth scopes held by the application's tokens. Any Skill that can cause modification must go through the plan → approval → execution architecture, may not hold or request write tokens itself, and must not bypass dry-run. See [SKILLS.md](SKILLS.md).

## 7. Incident response (outline)
1. Revoke OAuth access in the Google account; delete local tokens.
2. Rotate Google Cloud client secret if exposed.
3. If a secret was committed: treat as compromised, rotate first; ask the owner before any history rewrite.
4. Record the incident in `docs/` (without secret values).
