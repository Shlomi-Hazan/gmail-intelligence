# M12D — Controlled bulk execution and bulk reversal

Issue #62 (related: #41). **Status: IMPLEMENTED BUT DISABLED**, verified only against synthetic data, a fake Gmail wire and mocked credentials. No real Gmail, OAuth or Keychain access ever happened; `LIVE_EXECUTION_ENABLED`, `LIVE_UNDO_ENABLED` and `LIVE_OBSERVE_ENABLED` are all `False` and independent. **Real Gmail behavior is unverified**; nothing here is a claim of production acceptance.

## 1. What already existed and was reused unchanged
Immutable plans, one-time approvals, the execution state machine with bounded slices (a canary of 25 for plans over 100, then slices of at most 100; a plan holds at most 500 items), the per-item archive executor (account check, per-item local revalidation, live message and whole-thread checks, durable intent, at most one request, independent execution-bound post-read, UNKNOWN on ambiguity), `confirm_slice` / `abort_execution`, the single-item undo engine, read-only recovery and reconciliation (`recover_observed`), the hash-chained audit log, trusted observations and the M12A/M12B discovery, review and plan creation.

## 3. Owner workflow — bulk archive (all steps typed; nothing continues automatically)
1. M12B: `cleanup preview` → `cleanup plan create --group ... --selection-digest ...` → `cleanup plan review` → `cleanup approve` (the reviewed selection and its digest are frozen in the plan).
2. `cleanup execute PLAN --dry-run`: operation, item count, slice sizes and boundaries, whether it is locally executable. Writes nothing.
3. `cleanup execute PLAN --reserve`: typed execution phrase consumes the one-time approval, freezes the targets, confirms slice 1. *Disabled in this build: refuses before the index, credentials or network.*
4. `cleanup exec run EXEC`: a SEPARATE typed run phrase for the confirmed slice (bound to plan hash, execution id and slice number); one bounded slice runs. *Disabled.*
5. Between slices `cleanup exec confirm EXEC`: a fresh typed continuation phrase for the next slice only (refused while anything uncertain or unsafe remains); then `exec run` again. *Disabled.*
6. `cleanup exec abort EXEC` (local) abandons an execution that is not running; `cleanup exec show` / `cleanup exec recovery` show status; `cleanup exec recovery --reconcile` settles uncertainty read-only (separate disabled switch).
Distinct operations: **continuing** to a not-yet-started approved slice needs a fresh owner phrase; **reconciling** an ambiguous item is read-only; **retrying** a mutation does not exist. An item that may have been dispatched is never retried; UNKNOWN stops the execution (remaining targets `NEVER_ATTEMPTED`); an expired lease never becomes permission (it becomes UNKNOWN work); a slice whose confirmation was recorded can never run twice; an execution cannot advance while an item is INTENT / UNKNOWN / CONFLICT / rejected or an earlier slice had no applied item.

## 4. Owner workflow — bulk reversal (`cleanup undo reversal ...`)
`create EXEC [--exclude-item N]` (local) freezes a plan from the verified `APPLIED` items of a FINISHED execution (trusted evidence, intact plan and consumed approval, original labels included INBOX, no open undo) — nothing else, never more later; `show REV` (local); `approve REV` (typed phrase, 24 h, lockout; executes nothing); `run REV` (typed fresh phrase per slice, one bounded slice per command, *disabled in this build*); `abort REV`. Sizes follow the archive rule. The plan lives in the append-only audit log (`REVERSAL_*` events) and is bound to the source journal by a digest; a changed journal makes it refuse. Per item the unchanged engine verifies the item, the live message and its whole thread before its own durable intent; **drifted or vanished items are skipped** (nothing is sent, recorded with a code); **UNKNOWN, a provably refused request or any read problem stops the slice and the whole plan** (remaining items never attempted); an ambiguous undo is never retried; a slice that never ended is INTERRUPTED (30 minutes) and can only be aborted. Restoring adds only INBOX; no other label, message or archive history changes.

## 5. F5 — thread rule
Undoing one archived message used to make its siblings' undo fail as drift (the thread check expects every archived sibling to stay archived). Now a sibling is expected at its ORIGINAL labels only if ALL hold: the reversal plan is genuinely approved in the audit log; the sibling's item ledger is in the strict state `RESTORED` (a completed, trusted, observed outcome; never UNKNOWN / OPEN / INCONSISTENT); and the authorization behind that outcome carries THIS plan's id (written only by the engine inside a running slice of that plan). Everything else is unchanged: any other change, an INBOX label added by someone else, a restoration by another plan, a protected-label sibling, a changed or foreign thread membership still makes the undo refuse as drift. The single-item undo (M12C.3) is as strict as before. *Rationale:* the proof of a sibling's restoration is the engine's own trusted post-read, bound to the same approved plan; trusting anything weaker (a label seen in Gmail) would let external changes pass as ours. *Limitation:* after a stopped or interrupted plan, a NEW plan cannot reuse the old plan's restorations as proof, so such siblings stay refused (fail-safe) and are done by hand.

## 6. Recovery integration
Local status (`cleanup exec recovery`) now also lists reversal plans and stays available with no Gmail connection. Live reconciliation of uncertain archive or undo items is read-only through the observe-only capability (`recover_observed` / `reconcile_undo_observed`); no reconciliation command sends a mutation. Interrupted executions are never resumed; an interrupted reversal is never resumed.

## 7. Verified synthetically / not verified
Verified (`tests/test_bulk_execution.py`, `tests/test_bulk_reversal.py` and the unchanged M4/M12C suites): multi-slice plans of 130 and of the 500-item maximum with separate approvals, wrong/stale/foreign phrases and lockout, drift and changed-label skips, an ambiguous result stopping everything, interrupted executions not resuming, a concurrent-change recompute, evaluation reuse (a handful of full evaluations per slice instead of one per item), reversal creation limited to eligible items, approval and expiry, multi-slice reversal restoring only INBOX, the F5 cases (sequential siblings, external sibling drift, protected sibling, an arbitrary INBOX label, restoration by another plan, an unsettled sibling, a forged plan id), ambiguous / interrupted / aborted-while-running reversals, wrong account, gates, privacy-safe output, valid audit chain and unchanged archive history.
**Not verified:** anything against real Gmail (response behavior, quotas and rate limits, eventual consistency, latency of 500-item runs), real credential lifetimes during long slices, and real-mailbox canaries.
