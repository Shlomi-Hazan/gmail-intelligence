# M12C consolidated security audit (M4 + M12C.1-M12C.4)

Issues #61 and #41. Scope: the finished M4 execution/recovery stack plus the M12C additions (archive undo, read-only observation, token renewal). Method: code reading of the policy, transport, adapter, executor, recovery, undo, audit, credential and CLI layers; the existing and new guard/regression tests; synthetic end-to-end scenarios over a fake Gmail wire. **Nothing was exercised against real Gmail, OAuth or the Keychain.** This audit is advisory evidence for the owner's decision, not a certification; in-process guards are barriers against mistakes and ordinary callers, not against code running in the same process.

Severity: Critical / High (exploitable or wrong mutation) / Medium / Low / Info. **Result: no Critical or High finding.** Two Low findings were fixed in this change; the rest are accepted limitations or recommendations.

## Findings
| # | Sev. | Component | Finding | Resolution |
|---|---|---|---|---|
| F1 | Low | `cli.py` `auth refresh-write` | The M12C.3 renewal command read its typed confirmation with plain `input()`, so a piped/scripted phrase could renew the write token without a person at a terminal (plan review/approval already use the terminal-only `_tty_input`). Evidence: the command's source; reproduced by feeding stdin. Risk: renewal alone enables nothing (all gates off, scope unchanged) but weakens "explicit owner intent". | **Fixed**: terminal-only confirmation; EOF/non-terminal refuses with a fixed message and changes nothing. Test: `test_piped_or_scripted_input_never_renews_a_credential`. |
| F2 | Low | `gmail_write.fetch_profile_email` | A single profile read built an ARCHIVE-capable transport (least privilege). It could never mutate (unverified, no expected account) but held a mutation capability. | **Fixed**: it now uses the read-only OBSERVE capability. |
| F3 | Low | `cleanup_live.recover_live`, `reconcile_undo_live` | Live recovery/reconciliation was reachable only through mutation-capable mailbox types (archive or undo), mixing read-only work with objects that can mutate and tying recovery to the mutation switches. | **Addressed**: new OBSERVE capability, `LiveObserveMailbox` and `LIVE_OBSERVE_ENABLED`; the CLI uses only `recover_observed` / `reconcile_undo_observed`. The two older functions are no longer called by production code; recommended for removal in M12D (kept now to avoid churning merged tests). |
| F4 | Low | audit log | The hash chain plus DB triggers detect and refuse edits/deletes of existing rows, but cannot detect truncation of the tail or a complete rewrite by someone who controls the SQLite file. | **Accepted**; mitigated by the optional checkpoint (`cleanup audit verify --checkpoint`), file permissions and the documented threat model. |
| F5 | Low | `cleanup_undo._undo_item` + `cleanup_executor._thread_problem` | By inspection (not exercised by a test): after one item of a thread is restored, the thread check expects every item archived by the same execution to still be in its archived state, so undoing a sibling in the same thread is refused as drift. Fail-safe (a refusal, never a wrong mutation) but it would block bulk undo of threads. | **Open, deferred to M12D** (needs a deliberate rule that treats a restored sibling as expected); no change made here. |
| F6 | Medium (inherent) | write grant | The only write scope Google offers for this is `gmail.modify`, much broader than the allowlisted requests; the allowlist is an application policy, not a Google limit. | **Accepted, documented** (login warning, separate Google project, separate Keychain item, 10-minute validity floor, revocation command). No scope was added. |
| F7 | Info | tests/seams | `undo_cli.dispatch` and `reconcile_cli` accept a `mailbox_factory` for offline tests. The gate is checked first and the mailbox type/wiring is re-checked by the engine, so a seam cannot bypass it; the ordinary CLI never passes it. | Accepted. |
| F8 | Info | `GMAIL_INTELLIGENCE_HOME` | The only environment variable read (app data directory). It cannot enable a gate. | Accepted. |
| F9 | Info | `login-write`, `revoke-write` | These older commands still use plain `input()`. Login needs a browser and a person; revoke only removes access. | Recommendation: align with `_tty_input` in a later change. |

## Review by area
**A. Write-policy allowlist.** Four routes; the modify route accepts exactly two byte-for-byte bodies (`{"removeLabelIds":["INBOX"]}` archive, `{"addLabelIds":["INBOX"]}` undo), classified as separate kinds; every request needs a fixed `fields` projection; hosts/paths/queries/headers/redirects are pinned; no Trash, untrash, delete, batch, send, draft, label creation. Evidence: `test_write_transport`, `test_undo_infrastructure` (policy near-miss bodies, other endpoints), source scans in `test_cleanup_recovery`. Capability separation: a transport holds exactly ONE of ARCHIVE / UNDO / OBSERVE (construction refuses empty, unknown, repeated, string and combined sets); the transport refuses the other mutation before any dispatch, twice; the OBSERVE transport can send no mutation at all; each live mailbox type is final and its wiring (types, capability, factory, account) is re-verified before use.

**B. Authorization.** Read and write grants are separate (client file, project attestation, Keychain item, exact-scope checks, client fingerprint). Typed owner approvals: plan review/approval, execution, canary and undo each have their own phrase; undo and archive authorizations never substitute for each other (tested). Tokens: a 10-minute validity floor at adapter construction, the transport refuses an invalid token on every request (`dispatched=False`), nothing refreshes in the background, `auth refresh-write` is explicit, typed on a terminal, pinned to Google's token endpoint, scope-checked and replaces the stored record only after validation. Account identity: stored account, live profile comparison before any mutation or observation, issuer bound to the account (wrong-account tests). Gates: disabled operations refuse before the index, the credential store or the network.

**C. Execution and recovery.** Durable intent before every mutation (tests: intent written before the POST); at most one attempt per item; no automatic retry/resume (a second attempt is refused, an interrupted item is `OPEN`/`UNKNOWN` and resolved only by observation); independent post-read bound to execution, item and phase (cross-phase, foreign-context and wrong-account evidence rejected); `UNKNOWN` stays `UNKNOWN` without usable evidence; `CONFLICT` is final and visible; expired leases become reconciliation work and are never resumed; reconciliation (`recover_observed`) only reads and appends local results (tests assert zero POST/UNDO requests). An HTTP 200 never proves an outcome.

**D. Audit integrity.** Hash-chained rows, DB triggers refuse update/delete, original execution history never rewritten (undo and recovery append only), inconsistent undo ledgers are detected and reported, never acted on. Limitation: F4.

**E. Privacy and operational safety.** Metadata only (labels, thread ids, sizes, dates, the From header for classification); fixed-text errors that never echo input, ids, URLs or tokens; default outputs contain no message ids, addresses or labels (local execution ids may appear); no secrets in logs (no logging module use in the write path); tests run behind socket guards and bomb replacements for the Gmail reader and Keychain; Zero Additional Cost (standard library; the optional AI client is loopback-only).

## Not verified / remaining prerequisites
Before ANY real Gmail acceptance: (1) the owner's separate written authorization for each live capability; (2) a real-mailbox canary plan for undo and for observation (single message, throwaway account) with explicit abort criteria; (3) confirmation of Gmail's real answers, quotas and consistency for the undo request and the minimal reads; (4) an explicit decision on F5, F9 and the removal of the legacy live functions; (5) re-running the Keychain/OAuth setup checklist. Before bulk execution (M12D): the reviewed immutable plan model, the bulk-undo reversal plan (see `M12C-UNDO-DESIGN.md` section 7), the thread-rule decision (F5), bounded slices with per-slice confirmation, and the per-message revalidation just before acting.
