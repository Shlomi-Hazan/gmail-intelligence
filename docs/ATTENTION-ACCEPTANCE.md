## 3. Conclusion (as of the original review at `bfbcd09`)
No finding allows a write, a network call, a change to the index, a traceback or a partial result presented as complete. The two privacy findings (F1a, F1b) concern stored text appearing in an error message or output when the index itself is corrupted; they contradict two explicit acceptance criteria of #51 and had a small, local fix that this review did not apply itself (the engine was left unchanged, as instructed); the fix followed after the owner's authorization and is described in section 4.

## 4. Fix of F1a and F1b (commit `3b6d354`, pushed to PR #54)
* **F1a root cause:** `cmd_mailbox_attention` caught every `ValueError` to report bad parameters and printed its text; a `ValueError` raised while processing stored data (`strptime` on `scans.finished_at`, any `UnicodeDecodeError`) took the same path. **Fix:** `attention.ParameterError(ValueError)` is raised only by the parameter validation, whose texts are built from constants; the command prints only `AttentionError` (fixed codes) and `ParameterError`. Every other exception, `ValueError` included, falls through to the existing generic message. Exit codes are unchanged (1 for failures, 2 from argparse).
* **F1b root cause:** `types` and `signals[].rule` were copied from the stored rule rows. **Fix:** types are shown only if they are in `classify.TYPES`, rule ids only if they match the contract of `classifier.add_rule` (`u` and one to nine ASCII digits); anything else is shown as `UNRECOGNISED`, in JSON and in text. Scoring, the snapshot (which still uses the stored value), cursors, sender diversity, weights and the budget are untouched.
* **Audit of every output field derived from stored data** (no further direct reflection found): `items[].sender.display` and `.domain` (the stored sender, masked by default and sanitised with `clean()`; the domain is shown by design; the full address only with `--reveal-senders`), `items[].date` (formatted from an integer), `freshness.as_of` (only a string that parsed as the exact timestamp format can reach it, otherwise the report fails with the generic message), `freshness.sync_state` (a fixed label), `warnings`, `flags`, `evidence`, `tier`, signal codes and `components` (constants and integers), `rule.confidence` (reaches the output only if it is LOW, MEDIUM or HIGH, otherwise scoring fails closed), `ruleset_hash` and `snapshot` (digests).

## 6. CI run 40383476752 (Python 3.14, Linux): two failures caused by leaked SQLite connections
* **Failures:** `test_attention_cli.OutputTests.test_identical_snapshots_give_identical_output` (M8A-1) and `test_report_failure_boundary.BoundaryTests.test_unexpected_error_in_a_deep_check_and_in_the_account_lookup` (M7, PR #50). Both compare the captured stderr of a CLI call exactly; a `ResourceWarning: unclosed database` was printed into it.
* **Root cause (evidence, not an assumption about timing):** a connection that is dropped without `close()` on an error path is cyclic garbage: it is NOT finalised when its last reference goes (0 warnings immediately, 1 after `gc.collect()`, Python 3.13 and 3.14), only when the cyclic collector next runs, which can be inside any later test. Allocation tracebacks (tracemalloc) of every leaked resource in the suite, per test, give two classes:
  * **Production defects (open connection on an error path, pre-existing, NOT fixed here, awaiting approval):** `ReadOnlyIndex.__init__` (`index.py`, the `except sqlite3.DatabaseError` branch raises `IndexProblem` without closing `self.conn`) reached from a damaged file or a locked database (`test_analytics`, `test_dashboard_security`, `test_attention_corrupt_metadata`), and `maintenance._file_checks` (`maintenance.py`, the `except sqlite3.Error` branches return without `conn.close()`; 4 tests of `test_maintenance`). Proposed production fix: close the connection before raising or returning in those branches (about three lines).
  * **Test-fixture defects (fixed):** `Index` objects not closed (`test_plan_impact`, `test_deterministic_ties`/`organization_bench` per-account loop), a `ReadOnlyIndex` not closed (`test_dashboard_server`), `sqlite3.connect` not closed (`test_maintenance`), an unclosed file in a helper (`test_maintenance.tree_state`), and unread subprocess pipes after a kill (`test_cleanup_exec`, `test_cleanup_hardening`). File and pipe leaks are finalised immediately (reference count), so they warn inside their own test and cannot contaminate another one; they were fixed for hygiene.
* **Reproduction:** with one `ReadOnlyIndex(damaged file)` leaked and the collector run inside the call, both failing tests fail with the CI message shape on Python 3.14.0 and 3.13.5; collecting right after the leaking test makes them pass.
* **Test-side isolation (not a fix of the defect):** the seven tests that trigger the production leaks carry `@isolate_known_leaks` (`tests/leak_support.py`): the leaked object is finalised right after the test that caused it, with ResourceWarning ignored for that one `gc.collect()` only. Nothing else is suppressed; `GI_REPORT_KNOWN_LEAKS=1` shows them. When the production defects are fixed the decorator can be removed.
